03 — VISUAL DESIGN SYSTEM

3.1 Core palette

Create a consistent palette using these starting values. Adjust individual shades when necessary for legibility and visual balance.

- Absolute black: #030305
- Primary background: #07080B
- Secondary background: #0C0D12

- Primary text: #F7F7FA
- Secondary text: #A4A7B3

Do not make the whole application purple, blue, or gold. Black and translucent glass must remain dominant.

Avoid making every card equally bright. Establish depth through differences in surface luminance, blur, transparency, edge reflection, elevation, and contrast.

Use semantic color tokens instead of scattering arbitrary hexadecimal values throughout the code.

Support system light/dark configuration where appropriate, but make the application's intended premium dark appearance its primary experience.

3.2 Background environment

Create a sophisticated dark background with layered atmospheric depth.

Use a combination of:

- Near-black foundational color.
- Subtle radial illumination behind important content.
- Low-contrast ambient gradients.
- Soft, restrained reflections.
- Optional extremely slow ambient light movement.
- Localized illumination around the active music artwork.
- Subtle vignette to keep attention on the content.

The background must not compete with text or album artwork.

Ambient animation should move slowly and quietly, approximately 12–24 seconds per complete cycle where appropriate.

Do not continuously animate every background layer independently. Use a small number of coordinated effects.

Prevent visible gradient banding. Use suitable rendering techniques and subtle noise only when beneficial and inexpensive.

Avoid constant particles, distracting stars, excessive lens flares, and gaming-style visual clutter.

3.3 Typography

Use a sophisticated, highly legible typographic system.

- Large editorial titles with restrained weight.
- Medium-weight section headings.
- Carefully balanced title and artist typography.
- Compact, readable metadata.

Use available system typography or a bundled font only when its license and project integration are appropriate.

Do not imitate proprietary system fonts by distributing unlicensed font files.

Typography must adapt to screen size and system font scaling. Never sacrifice accessibility for a cinematic appearance.

3.4 Spacing and shape language

Create a coherent radius system.

Suggested starting points:

- Small controls: 12–16 dp.
- Standard cards: 20–24 dp.

4.1 Material composition

Each major glass surface should combine only the layers needed for its visual role:

1. A translucent base tint.
2. A backdrop blur where supported and performant.
3. A soft internal luminance gradient.
4. A subtle top-edge highlight.
5. A faint lower-edge shadow or reflective border.
6. A realistic shadow separating the surface from the background.
7. Optional directional specular lighting.
8. Carefully clipped rounded corners.

Create convincing depth through overlapping surfaces and lighting rather than merely applying a large blur radius.

The underlying background should remain perceptible through glass where appropriate.

Use restrained white edge highlights, with greater brightness near the light-facing edge and softer falloff elsewhere.

4.2 Glass physics and reflections

Where practical, create lightweight simulated reflections using gradients and carefully positioned highlight shapes.

Use subtle parallax or pointer/touch-relative lighting only on appropriate elements.

Reflections should follow a consistent virtual light direction. Do not allow each card to have unrelated lighting.

During a press, selected surfaces may temporarily increase their highlight intensity and apparent depth.

During drag interactions, selected glass sheets may follow the finger with a subtle liquid-like response.

On release, surfaces should return smoothly to their resting position.

Do not pretend to perform real-time optical refraction if the implementation only uses a gradient. Simulated reflections should still look sophisticated.

4.3 Backdrop blur requirements

Use native, compatible blur techniques where available.

Prefer localized clipping and small blur regions over full-screen blur.

If reliable live backdrop blur is unavailable on a supported Android version, use a layered translucent surface, subtle gradient, and edge highlights as a graceful fallback.

Do not blur text, album titles, playback controls, or important interactive content.

Do not blur the entire screen continuously.

Avoid expensive nested blur effects and repeated off-screen rendering.

The application must remain smooth on mid-range Android devices.

05 — MOTION DESIGN SYSTEM

Create a centralized motion system with reusable timing, easing, spring, and transition specifications.

Do not scatter arbitrary animation durations throughout the code.

Use native Compose animation APIs where appropriate, including animate*AsState, updateTransition, Animatable, AnimatedVisibility, Crossfade, and suitable navigation transition APIs compatible with the project's existing versions.

Suggested starting motion profiles:

- Instant tactile response: approximately 60–100 ms.
- Small icon state transition: 120–180 ms.
- Button press and release: 100–180 ms.
- Standard content entrance: 220–320 ms.
- Navigation transition: 300–450 ms.
- Glass-sheet presentation: 350–550 ms.
- Artwork morph: 350–600 ms.
- Large cinematic transitions: 450–700 ms, used sparingly.
- Ambient movement: 12–24 seconds per cycle.

These values are starting points, not rigid rules. Tune easing, distance, and duration to achieve the intended effect.

Use spring animations with appropriate damping and stiffness for tactile movement. Use smooth, carefully chosen easing curves for controlled transitions.

Avoid making all elements move simultaneously.

Use staggered entrance animations for related content, with short delays of approximately 25–60 ms when they improve hierarchy.

Do not animate every item in a long scrolling list whenever a recomposition occurs.

Do not restart animations unnecessarily when unrelated state changes.

5.1 Motion principles

Every animation must follow these principles:

- Immediate acknowledgment of input.
- Smooth acceleration and deceleration.
- Consistent spatial direction.
- Minimal overshoot for premium interactions.
- Clear separation between foreground and background movement.
- No sudden visual jumps.
- No flicker or abrupt alpha changes.
- No layout instability.
- No accidental repeated entrance animation.
- No motion that obstructs playback controls.
- No mandatory long animations before an action can complete.

The app should feel alive, not restless.

06 — GLOBAL INTERACTION ANIMATIONS

Implement the following behavior across the application.

6.1 Touch-down response

When a user presses an interactive surface:

- Respond immediately.
- Scale the surface subtly, typically to approximately 0.97–0.99 of its resting size.
- Increase the relevant glass highlight.
- Adjust elevation or shadow slightly.
- Provide a brief, appropriate haptic tick where supported.
- Avoid excessive bounce.

6.2 Release response

On release:

- Return smoothly to the original scale.
- Restore the default lighting.
- Settle the shadow without a sudden jump.
- Keep the action responsive even if an animation is still settling.

6.3 Focus and selection

For selectable chips, tabs, playlist rows, and navigation destinations:

- Animate the selection indicator.
- Use a restrained background morph.
- Transition icon and text emphasis smoothly.
- Preserve stable layout dimensions whenever possible.
- Make the selected state immediately identifiable.

6.4 Disabled controls

Disabled controls must look intentionally inactive.

Use restrained opacity and reduced contrast, not dramatic blur or movement.

Do not provide misleading haptic feedback for an unavailable action.

6.5 Long press

Where long-press behavior is useful:

- Provide a short tactile acknowledgment.
- Reveal a context menu or additional action.
- Use a smooth scale or elevation change.
- Ensure that long press does not interfere with normal tapping or scrolling.

6.6 Drag and reorder

For reorderable playlists or queue items:

- Lift the active item slightly.
- Increase shadow and edge illumination.
- Follow the drag gesture.
- Animate neighboring items out of the way.
- Use subtle haptic ticks when crossing valid reorder positions where supported.
- Settle the item naturally when released.

6.7 Double tap

Use double-tap gestures only when they have an unambiguous purpose.

Do not introduce hidden gestures that accidentally trigger playback, navigation, or destructive actions.

20 — PERFORMANCE ENGINEERING

Visual excellence is meaningless if the application stutters.

The app must remain responsive during scrolling, navigation, artwork changes, and playback.

Use the following requirements:

1. Use LazyColumn, LazyRow, or suitable lazy containers for large collections.
2. Use stable keys for repeated list items.
3. Avoid unnecessary recompositions.
4. Keep expensive calculations out of frequently recomposed UI.
5. Avoid repeated bitmap decoding on the main thread.
6. Cache artwork appropriately and respect memory limits.
7. Avoid creating unnecessary Animatable objects during recomposition.
8. Avoid multiple simultaneous full-screen blur passes.
9. Limit continuous animations to a small number of visible elements.
10. Pause animations when the relevant screen is not visible.
11. Use lifecycle-aware state collection.
12. Avoid blocking the main thread with file scanning, database operations, or artwork processing.
13. Avoid unnecessary wake locks, background services, and high-frequency timers.
14. Use appropriate image sizes and clipping.
15. Test the most animation-heavy screens on an ordinary Android device.
16. Ensure that navigation and playback controls remain responsive during animation.
17. Avoid memory leaks from animations, listeners, or long-lived coroutine scopes.
18. Preserve battery life when the application is idle or running in the background.

Do not claim a specific frame rate without measuring it.

Aim for smooth 60 Hz interaction on supported devices. Higher refresh rates may be supported where the device and system allow them.

Avoid chasing maximum visual effects at the expense of consistent frame pacing.
